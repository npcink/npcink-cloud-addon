# 站内媒体识别自动续批工程规范

状态：2026-08-28 起生效。

## 1. 目的

本规范记录站内媒体识别从“每点击一次只处理一批”演进为“一次点击后后台自动处理剩余图片”的实现边界、计数语义、失败恢复和验证经验。

面向用户的合同只有一句话：管理员点击一次“继续识别剩余图片”后，即使关闭后台页面，系统也会使用受控小批次继续处理，直到全部完成、达到 Cloud 每日额度、离开执行窗口或遇到需要管理员处理的错误。

第一版默认批次为 10 张。批次小是为了缩短失败恢复距离并限制单次 Provider 成本，不代表用户必须重复点击。百万级或 1000 万级只描述计划的逻辑规模，不允许形成超大请求、单一长运行或一次性 WordPress 查询。

## 2. 所有权边界

| 组件 | 拥有 | 不拥有 |
| --- | --- | --- |
| WordPress / Toolbox | 媒体清单、附件权限、文件指纹、本地格式筛查、受控分页读取 | Provider、Cloud 额度、模型路由、Cloud 运行状态 |
| Cloud Addon | 一次点击入口、持久计划、WP-Cron 续批、当前 `run_id`、只读进度和恢复入口 | 第二套执行队列、计费真相、模型选择、WordPress 媒体写入 |
| Cloud | 识图执行、Provider、运行记录、日额度、后台执行窗口、失败分类、结果投影 | WordPress 媒体爬取、附件游标、WordPress 写入 |

Addon 中的计划是连接器级“续批意图”，不是新的 Cloud 任务系统。每个实际识图批次仍以 Cloud `run_id`、运行状态和额度为执行真相。

## 3. 计划与状态

同一站点最多存在一个活动计划。重复点击必须恢复现有计划，不能创建并发计划或重复扣费。

计划至少保留：当前页、总量估计、已提交数量、已复用数量、本地筛除数量、成功和失败数量、当前 `run_id`、当前状态、下次可执行时间与暂停原因。

状态对普通用户收敛为：

- 自动识别中；
- 已达到今日上限，下一可用时段继续；
- 已暂停，需要管理员处理；
- 识别已完成。

内部状态可以更细，但不得把 Provider、游标、向量、模型或批次参数推到首屏。

## 4. 顺序续批合同

执行顺序固定为：

```text
创建或恢复计划
  -> 立即返回管理员页面
  -> WP-Cron 接管首批和后续批次
  -> 读取下一页媒体
  -> 本地校验、筛查和指纹去重
  -> 提交一个 Cloud 识图批次
  -> 保存 run_id 并立即返回
  -> WP-Cron 轮询当前运行
  -> 合并完成结果
  -> 原子推进已确认游标
  -> 判断继续、等待、暂停或完成
```

必须满足：

1. 当前 `run_id` 未结束时不得提交下一批，也不得顺带启动重叠的 Site Knowledge 同步。
2. 浏览器 JavaScript 只负责刷新显示，不能承担续批循环；关闭浏览器后 WP-Cron 仍可继续。
3. 每批使用稳定幂等语义；重复点击、重复 Cron、状态轮询和不确定网络重试不得重复计数。
4. 失败只重试或回滚当前批次。未完成批次不能推进已确认游标。
5. 新增图片在后续清单页进入计划；指纹未变化且已有视觉证据的图片直接复用。
6. 管理员按钮不得同步上传整批图片。它只能创建或恢复计划并安排现有 WP-Cron；首批也属于后台工作。

## 5. 计数语义

一次逻辑清单页不等于本次提交给 Provider 的图片数。以下指标必须分开：

| 指标 | 含义 |
| --- | --- |
| `processed` | 已经完成本地决策的 eligible 图片，包括复用、识别成功和本地筛除 |
| `submitted` | 本批真正新提交给 Cloud 识图运行的图片 |
| `reused` | 指纹匹配并复用现有视觉证据的图片 |
| `screened` | 因格式或本地约束而未提交的图片 |
| `successful` | Cloud 本批成功产出识图结果的图片 |
| `evidence` | 当前可用于推荐的视觉证据总量 |
| `daily_used` | Cloud 当日已经消耗的图片额度 |

完成度使用 `processed / eligible total`；今日额度使用 `daily_used / daily_limit`。两者必须使用不同标签和进度语义，不能用额度进度替代清单完成度，也不能把逻辑页大小显示成 Provider 实际提交量。

## 6. 增量媒体生命周期

新图片或附件记录发生编辑时，Addon 只记录一次待重扫意图，并通过既有
`npcink_cloud_addon_continue_media_recognition` WP-Cron 唤醒完整清单检查。附件
hook 不得同步调用 Cloud，也不得建立按附件执行的第二套队列。

完整清单检查不等于重新付费识别全部图片：Toolbox 重新读取 WordPress 媒体
清单并计算文件字节指纹，指纹未变化且已有视觉证据的图片直接复用，只有新增或
字节发生变化的图片才进入新的 Cloud 识图批次。

必须满足：

1. 未验证 Cloud 设置、未启用站点知识库投递或非图片附件不得启动识别计划。
2. 同一附件重复触发 `add_attachment` / `edit_attachment` 时只保留一个触发标记。
3. 当前清单检查尚未完成时，其他附件变化只记录一次待重扫，不改变当前游标。
4. 当前检查完成后，待重扫标记原子启动一次新清单检查；暂停或错误状态不得并发启动第二个计划。
5. 触发附件 ID 只作有界诊断与幂等标记，最多保留 100 个，不成为媒体清单真相，也不得进入遥测。
6. 附件删除继续复用既有 `before_delete_post` Site Knowledge 变化桥接；Cloud 删除匹配投影，WordPress 仍是附件存在性真相。

第三方插件若绕过 WordPress 附件更新 API，直接在原路径覆盖文件，不保证立即
产生附件事件。管理员执行“检查新图片”或后续正常附件事件时，完整清单检查仍会
通过字节指纹发现变化。没有真实用例证据前，不增加宽泛的 post-meta 监听或独立
周期扫描。

## 7. 输入筛查与隐私

- 仅将 Cloud 视觉运行明确支持的 JPEG、PNG、WebP、AVIF 提交识别；GIF 等不支持格式在 WordPress 本地筛除。
- 本地站点不可从 Cloud 访问时，使用现有短时 Artifact 上传，不退化为发送内网站点 URL。
- 识图上传优先选择 WordPress 已生成、文件不超过 256 KiB 且像素面积最大的派生图；语义缓存和变更检测仍使用原图字节指纹。没有合格派生图的本地附件在本地筛除，不能退化为不可访问 URL。
- Artifact 文件名使用有界合成名称，例如 `site-media-{attachment_id}.jpg`；不得把过长中文文件名或不必要的原始路径带入上传。
- 埋点只记录生命周期、数量、延迟、速度、错误代码和版本，不记录图片内容、图片 URL、Prompt、完整模型输出、附件 ID、文章 ID、用户 ID、凭据或原始 Provider 错误。

## 8. 失败恢复

临时轮询基线可以包含本批的 `reused` 和 `screened` 数量，但只有 Cloud 运行成功结束后才能提交为计划进度。运行失败时必须恢复到上一已确认页，避免出现“失败了但进度增加”或重试后双重计数。

错误分层：

- 每日额度为零或不在执行窗口：等待 Cloud 返回的下一可执行时间；
- 积分不足：暂停并提示管理员处理；
- 模型未验证、Provider 不可用或确定性输入错误：进入错误状态，不做无界重试；
- 短暂网络或轮询失败：保持当前 `run_id`，使用现有有界 Cron 恢复。

若 Cloud 已接受运行，但响应在返回 WordPress 前超时，本地可能暂时没有
`run_id`。这类结果不确定的传输失败必须保留当前页和已确认计数，通过同一个
WP-Cron hook 退避重放同一指纹批次。Addon 为当前传输尝试保存稳定
`upload_attempt_id`，Toolbox 将它与附件、原图指纹及上传字节摘要组合为稳定幂等键，
从而复用既有 Artifact
与 Cloud run；只有收到明确响应后才能保存 `run_id` 和继续推进游标。确定性错误
仍然暂停，不能套用这条自动重放规则。

`upload_attempt_id` 只属于本地短时传输语义，不是新计划 ID、Cloud Artifact 真相或
计费真相。自动退避重试必须复用它；管理员在计划暂停后显式点击“重试本批”时必须
生成新的值，以免 30 分钟 Artifact 已过期后永久重放旧上传键。函数内部不得再做
盲目的第二次同步上传，重试统一交给持久计划和 WP-Cron。

不得通过提高并发、扩大批次或增加另一套队列掩盖边界、幂等或计数错误。

## 9. WP-Cron 的限制

WP-Cron 是机会式调度：本地开发站或低流量站点可能在一段时间内没有请求，因此续批看起来会短暂停住；之后有页面访问或系统 Cron 触发时会继续。这解释了测试中进度从 62 延迟到 68 的现象，不是浏览器按钮在后台偷偷执行。

生产低流量站点应由服务器定时请求 `wp-cron.php`，但 Cloud 不应直接控制 WordPress Cron，也不应因此在 Addon 增加新的调度设置界面。平台现有全局时区、后台窗口和每日上限继续由 Cloud 管理。

## 10. 用户界面规范

首屏只回答：处理了多少、总共有多少、当前是否自动继续、今日额度是否阻塞、预计下一步是什么。进度组件在概览与媒体页必须读取同一投影，样式和百分比保持一致。

Cloud `run_id`、本批提交/复用/筛除、速度、预计批次完成时间、模型与错误代码放在“查看识别详情”中。刷新按钮只刷新显示；启动或恢复计划使用唯一的“继续识别剩余图片”动作。健康运行时不要求用户再次点击。

## 11. 放量与验证

容量按 `1,000 -> 10,000 -> 100,000` 逐级验证，再评估百万级。每一级必须检查断点续跑、游标准确、重复识别、额度、失败回滚、数据库压力、Provider 成本和平均完成时间。

合并前至少验证：

- Toolbox 的静态合同、PHP 语法和 Provider 错误行为；
- Addon 的计划、回调、状态投影、中文文案、Playground 激活和发布包；
- 同一站点不会出现两个活动计划或两个并发 Cloud 运行；
- 重复点击、刷新和重复 Cron 不重复提交；
- 关闭浏览器后仍能续批；
- 达到额度后等待，下一周期能够恢复；
- 概览和媒体页显示同一完成度。

2026-08-30 的只读复核发现，当前计划实际为 `69 / 71`，其中 68 条视觉证据、
0 条失败；本地媒体库存共 71 条，只有附件 `1692` 明确是当前不支持的
`image/gif`，其余 70 条均有支持 MIME、有效 URL 和本地文件。另有 1 条支持格式
媒体没有在现有计划投影中计入，具体附件和原因尚未从历史批次结果中确认。
在补齐逐图片筛查/批次结果证据前，不得把当前状态写成 70 / 70 或 69 / 69。

本次现场复核还发现，测试附件 `287536` 的创建时间与计划启动时间同为
`2026-08-29 22:08:08`，并在当前按日期倒序的库存中位于第 1 条。新增附件插入
清单头部会使基于页码的游标发生漂移，可能造成支持格式图片被跳过或重复；后续
应改为稳定快照/稳定排序游标后，再重新验收 `eligible_total` 和最终完成度。

这次调试得到的核心经验是：先修复运行身份保留、顺序续批、失败回滚和计数语义，再讨论更大的批次或套餐额度。用户感受到的“自动化”来自可恢复的小步执行，不来自一次提交海量图片。

2026-08-30 的第二轮现场诊断确认了首批传输阻塞：一张 1,641,587 字节 PNG 经
Tailscale DERP/peer relay 上传需要约 54 至 151 秒，而 Addon 的 WordPress HTTP
超时为 30 秒。管理员页面已显示失败后，遗留 PHP 请求仍继续逐张上传原图，重复
手势还触发了 Cloud `media_upload_conn` 429；期间没有创建视觉 Provider 调用，也
没有产生图片识别计费，但形成了多条零额度上传运行。根因不是 Cloud 续批队列，
而是首批仍在管理员请求内同步上传、Toolbox 固定使用原图、上传重试键含随机 UUID。
修复因此固定为“按钮只排计划、Cron 执行首批、上传小派生图、计划内稳定重放”，
而不是提高批次、延长页面等待或让 Cloud 控制 WordPress Cron。

2026-08-29 在 `magick-ai.local` 对真实已验证设置执行了事务内、无 Provider
附件事件 smoke：完成态计划收到一个真实图片附件事件后进入 `partial`，从第 1 页
开始，保留一个触发标记且没有 `run_id`。事务回滚后原有 `complete`、70 / 70 和
