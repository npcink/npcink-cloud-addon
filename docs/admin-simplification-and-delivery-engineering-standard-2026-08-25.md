# Cloud Addon 后台简化与交付工程规范

状态：Accepted（2026-08-25）

适用范围：`npcink-cloud-addon` 的 WordPress 后台设置、Site Knowledge
自动投递、Cloud 详情跳转、本地化、测试、合并和 PR 交付。

当前界面标准以 `docs/admin-surface-standard.md` 为准。本文记录本阶段为什么
这样设计、开发中出现过什么问题，以及以后如何避免重复犯错。

## 1. 阶段结论

Cloud Addon 面向 WordPress 站长和普通运营人员，不面向 Cloud
运行时工程师。后台只需要帮助用户完成三个任务：

1. 连接并确认 Cloud 服务可用；
2. 确认站点知识内容是否在自动更新；
3. 在真实失败时执行一次明确的恢复操作。

因此，Addon 后台不是 Cloud 控制台的缩小版。索引运行、运行记录、Provider
细节、重试策略、索引生命周期和技术诊断真相留在 Cloud；WordPress 只展示
与当前站点直接相关的简明状态、本地授权和有界投递结果。

本阶段最终采用以下产品模型：

- 已验证后只保留 `概览`、`站点知识库`、`高级与排查` 三个顶层入口；
- `站点知识库` 开关打开时显示对应菜单，关闭时不显示该菜单；
- 文章、页面和已批准评论变化后自动触发知识库更新；
- 健康状态不展示常驻“立即更新”或“重试”按钮；
- 只有记录到真实投递失败时，才展示一次恢复更新操作；
- Runtime Runs、索引执行详情和技术运行记录不在 WordPress 展示；
- Cloud 详情使用当前站点的 Portal 地址，而不是无上下文的通用页面；
- 普通状态和额度摘要放在概览，低频设置与诊断放在高级区域。

## 2. 用户语言与心智模型

### 2.1 先说用户要解决的问题

用户进入页面通常不是为了“管理队列”“触发 Runtime Run”或“执行同步任务”，
而是为了确认：网站内容是否已经能被 Npcink AI 使用。

设计和文案应按以下顺序组织：

```text
当前是否正常 -> 最近是否更新 -> 是否需要我处理 -> 去哪里看详细信息
```

不得按内部实现顺序组织：

```text
buffer -> cursor -> runtime run -> retryability -> vector lifecycle
```

### 2.2 命名规则

- 面向用户使用“站点知识库”描述整体能力。
- 需要明确动作对象时使用“知识库索引”。
- 不使用含义过宽的“同步”，它无法说明同步的对象和结果。
- 不单独使用“索引”作为一级产品名称，避免与 SEO 搜索引擎收录混淆。
- “更新知识库”可以作为恢复动作，但不能暗示 WordPress 本地拥有索引执行权。
- `buffer`、`cursor`、`run_id`、`retryable`、Provider 和 contract id
  只属于技术详情、日志或测试，不进入普通状态文案。

### 2.3 状态必须对应真实事实

至少区分以下四层事实：

| 层次 | WordPress 可展示内容 | 真相所有者 |
| --- | --- | --- |
| 连接 | 是否已配置、最近验证是否成功 | Addon 本地验证状态 |
| 投递 | 是否有失败、最近一次有界投递时间 | Addon delivery buffer |
| 索引 | 索引执行、完成度、生命周期、freshness | Cloud Site Knowledge |
| 使用 | Cloud 额度和只读服务摘要 | Cloud entitlement |

“凭据验证成功”不能写成“知识库已更新”；“请求已投递”不能写成“索引已完成”。
本地缓存只能作为摘要或恢复依据，不能冒充 Cloud 当前真相。

## 3. 信息架构与动作规范

### 3.1 概览

概览回答“现在能不能正常用”：

- 一条紧凑的连接状态；
- 常用额度和服务摘要；
- 一个站点知识库启用开关；
- 只有需要处理时才出现的注意项；
- 一个进入 Cloud 的明确入口。

健康状态不重复展示验证时间、成功上传时间、内部状态码或技术解释。

### 3.2 站点知识库

站点知识库回答“内容是否在自动更新”：

- 当前自动更新状态；
- 最近一次成功投递时间；
- 失败时的原因摘要和一次恢复操作；
- 指向当前 Cloud 站点知识库详情的链接。

文章、页面和评论列表不增加常驻知识库菜单、批量操作或行内按钮。内容变化本来就
会自动投递，额外入口会把自动能力重新包装成需要人工维护的任务。

以下内容默认不展示：

- 健康状态下的“立即更新知识库”；
- 没有失败时的“重试”；
- Runtime Runs 和运行记录；
- 索引阶段、Worker、Provider、重试次数等技术字段；
- 本地重建、删除、生命周期管理控制台。

### 3.3 高级与排查

只保留低频且确实由 WordPress 负责的内容：

- 连接检查和经过清洗的失败信息；
- 手工 Base URL/API Key 恢复入口；
- 本地隐私授权和监控投递状态；
- 本地断开连接；
- 指向 Cloud 技术详情的链接。

技术详情移到 Cloud 不是简单地“藏起来”，而是让信息回到真实所有者，避免
WordPress 和 Cloud 同时展示不同版本的运行真相。

### 3.4 动作层级

同一视图最多有一个主动作：

- 未连接：连接 Cloud；
- 已连接但异常：按原因给出一个恢复动作；
- Site Knowledge 投递失败：更新知识库；
- 健康：没有主动作，只显示状态和详情链接。

设置使用开关，模式使用分段控件，低频入口使用普通链接。危险操作与普通设置分区，
不得和健康状态下的常用动作并列。

## 4. 自动更新与恢复模型

自动更新的触发范围是已发布文章、公开页面和已批准评论产生的相关内容变化。
Addon 将变化转换为有界、可重放的公开内容投递；Cloud 决定如何建立和维护索引。

恢复操作存在的理由不是“自动化不可靠，所以总要留一个按钮”，而是给真实失败
提供明确出口。恢复入口必须同时满足：

1. 有持久化的失败事实，而不是页面刷新产生的瞬时猜测；
2. 用户有权限处理；
3. 操作复用已有有界投递路径，不创建第二套队列或同步机制；
4. 成功或失败都在原位置反馈；
5. 恢复后健康状态重新隐藏该入口。

页面渲染不得直接发 Cloud 请求。状态刷新使用已有只读缓存、明确的管理员操作或
既有 AJAX/Cron 路径。

## 5. Cloud 与 Addon 边界

Addon 可以拥有：

- 本地连接与加密凭据；
- Site Knowledge 本地启用授权；
- 有界公开内容变化缓冲和 WP-Cron 投递；
- 最近成功、失败和待恢复的浅层状态；
- 指向 Cloud 当前站点详情的链接。

Cloud 拥有：

- 索引执行和生命周期；
- freshness、重建、删除和完成状态；
- Runtime Runs、Provider 和 Worker 详情；
- 运行日志、深度诊断和服务侧重试策略；
- 额度与服务真相。

不得因为“用户可能想看”就在 Addon 复制 Cloud 控制面。先问：这个信息是否会改变
用户在 WordPress 里的下一步？如果不会，优先链接到 Cloud。

## 6. 本阶段开发问题复盘

### 6.1 页面复杂度来自逐项叠加

历史页面把每个后端能力都变成标签、表格或按钮，单项看似合理，组合后却让普通
用户无法判断主次。根因不是 CSS，而是没有以用户任务作为容量上限。

纠正方式：先删除不属于 WordPress 的控制和重复解释，再调整布局。视觉优化不能
替代信息架构简化。

### 6.2 自动能力被错误表达为人工任务

文章、页面和评论本来会自动触发投递，仍在多个位置提供手动入口，会让用户误以为
每次更新后都要操作。常驻重试按钮还会暗示系统处于不稳定状态。

纠正方式：正常状态静默自动化，失败状态才披露恢复动作。

### 6.3 术语跟着实现走

“同步”“索引”“运行记录”等技术词没有说明用户收益，其中“索引”还可能被理解为
SEO 收录。

纠正方式：产品名称使用“站点知识库”，具体过程使用“知识库索引”，技术名词只留在
支持事实中。

### 6.4 文本合并成功不代表语义合并成功

合并 `origin/master` 时，双方都修改了 Site Knowledge 和设置页。冲突文件选择主题
分支版本后，自动合并仍产生过重复方法和测试预期与实现不一致的问题。这类问题不会
全部表现为 Git conflict。

纠正方式：合并后必须重新做符号重复扫描、完整契约测试和关键行为检查；不能复用
合并前的绿色证据。

### 6.5 删除功能时遗漏发布清单

Runtime Runs presenter 已从源码、加载和测试中删除，但 `release-manifest.txt` 仍引用
旧文件。PHP、JS、i18n 和 Playground 都通过，最终 ZIP 构建才暴露问题。

纠正方式：删除可发布文件时使用“源码、bootstrap、测试、语言、文档、发布清单”
六点检查，并在提交前执行 `package:release` 与 `package:verify`。

### 6.6 自动合并与非必需检查存在竞态

PR #109 的 PHP 和正文检查通过，但 Release static gates 失败后 PR 仍自动合并，说明
该检查当时不是保护分支的必需门禁。修复只能通过 PR #110 追加。

纠正方式：

- 不把“已合并”当作“所有检查均通过”；
- 发布者必须查看完整 check rollup；
- 任一与本次范围有关的失败都视为未完成，即使 GitHub 允许合并；
- 删除发布文件的改动必须把 Release static gates 视为人工交付门禁；
- 分支保护应将 Release static gates 纳入相关路径的必需检查，或让汇总必需检查依赖它。

## 7. 标准开发流程

### 阶段 A：先定义用户任务

写出一行目标和一行非目标。例如：

```text
目标：让站长确认站点知识库是否自动更新，并在失败时恢复。
非目标：在 WordPress 管理 Cloud 索引运行和 Runtime Runs。
```

任何按钮、状态或字段不能直接支持目标时，默认不进入首屏。

### 阶段 B：画清真相所有权

在编码前列出：状态来源、写入所有者、用户动作、失败恢复、Cloud 跳转地址。无法说明
所有者的字段不得进入 UI。

### 阶段 C：先写行为合同

设置页测试至少覆盖：

- 顶层入口数量和名称；
- 健康状态隐藏恢复按钮；
- 失败状态只出现一个恢复入口；
- Runtime Runs 本地页面不存在；
- 站点知识库菜单受启用开关控制；
- Cloud 链接包含当前 `site_id`；
- 页面渲染零 Cloud HTTP；
- 固定中文文案和动态字段边界。

### 阶段 D：按状态而不是按组件验收

至少检查：未连接、已连接健康、自动更新中、投递失败、功能关闭、Cloud 不可用。
桌面和移动端都检查最长中文字符串、按钮层级、焦点和无 JavaScript 回退。

### 阶段 E：合并后重新验证

合并基线后按当前工作树重新生成证据：

```bash
composer run test:all
composer run smoke:playground
composer run check:wporg
composer run check:js
composer run i18n:check
composer run package:release
composer run package:verify
git diff --check
```

只运行与变更无关的宽门禁不能替代关键路径验证。删除或新增可发布文件时，打包验证
不可省略。

### 阶段 F：受控发布与关闭

- 只暂存当前任务文件；
- 提交前检查 cached stat 和文件名；
- 使用仓库 PR 模板和 `composer pr:publish`；
- 等待并检查所有 CI，而不只检查 PR 是否 merged；
- 合并后确认 `origin/master` 的实际 squash commit；
- 如果合并后发现遗漏，使用最小后续分支和独立 PR，不修改已合并历史。

## 8. 交付检查表

### 产品面

- 页面是否只回答用户当前任务？
- 健康状态是否没有多余按钮？
- 自动能力是否被表达为自动，而不是人工维护流程？
- 失败时是否只有一个明确恢复动作？
- “站点知识库”和“知识库索引”是否避免了 SEO 歧义？

### 边界

- 是否把 Cloud 运行详情错误复制到 WordPress？
- 是否新增本地索引、队列、重试或生命周期真相？
- Cloud 链接是否指向当前站点，而不是通用或失效地址？
- 页面渲染是否保持零 Cloud HTTP？

### 工程

- 行为测试是否覆盖健康、失败、关闭和未连接状态？
- 删除文件是否同步更新 bootstrap、测试、语言、文档和 release manifest？
- 合并后是否重新跑过完整合同和打包门禁？
- PR 的所有相关检查是否真正通过？
- 本地提交、远端分支、PR head 和 `origin/master` 是否属于同一交付链？

## 9. 后续开发原则

本阶段完成后，Addon 进入实际使用观察期。新需求应由真实使用问题触发，而不是因为
后端存在某个能力就增加一个入口。优先收集：用户是否能判断当前状态、失败后是否知道
下一步、Cloud 详情是否可达、自动投递是否可靠。没有证据表明当前三任务模型不足时，
不扩充标签、按钮或本地控制面。
